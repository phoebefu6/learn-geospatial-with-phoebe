Part 1 · covers polygon, multipolygon, ring, hole, and what the file holds

A boundary is a list of corners

5 min live

Rivermont is constructed; the file Mei opens is not. The URA subzone file is GeoJSON, 332 features, each one a subzone with a geometry and a set of attributes. A geometry of type Polygon is a list of rings; a ring is a closed list of [longitude, latitude] corners whose last point repeats the first. The first ring is the outer edge. Any ring after it is a hole, an area cut out of the shape. A geometry of type MultiPolygon is a list of those lists: one subzone made of several separate pieces, usually a mainland part and an islet with sea between. Counted in the file on 2026-10-22: 321 Polygon and 11 MultiPolygon features, 374 rings of which 13 are holes, 58,530 vertices in all, 55 distinct planning areas and 5 regions, and 50 subzones flagged CA_IND = Y for the Central Area. No crs member, so the convention from session 1 applies: WGS 84, longitude first.

The dataset page describes the layer as an "indicative polygon of subzone boundary" and explains the hierarchy: URA divides Singapore into regions, planning areas and subzones, each subzone "usually centred around a focal point such as neighbourhood centre or activity node". It also says something every count built on the file should carry as a footnote: the Master Plan looks 10 to 15 years ahead and "the planning boundaries may not coincide with existing developments". The attributes are OBJECTID, SUBZONE_NO, SUBZONE_N, SUBZONE_C, CA_IND, PLN_AREA_N, PLN_AREA_C, REGION_N, REGION_C, INC_CRC, FMEL_UPD_D, SHAPE.AREA and SHAPE.LEN, with no descriptions on the page, so what each means is read from the values. The dataset was created 2019-12-23, last updated 2025-12-03, and the page says "Data from Sep 2021".

Mei's first act is the one from session 1: print the counts before using any of them. 332 features. A number that arrives on a slide, in a brief or in somebody's memory is a claim about the file; len(f["features"]) is the file. When the two disagree, the file wins and the slide gets corrected, in writing, with the date it was counted. The desk's rule for a count is the same as its rule for a coordinate: it carries its source or it is not used.

Self-studyRings, holes and the closing point4 min▶

Open one Polygon feature and its coordinates is a list with one or more items; each item is a ring, a list of [longitude, latitude] pairs. A valid ring repeats its first pair as its last, which is why a square has five coordinates, not four, and why a ring with fewer than four pairs encloses nothing. Position zero is the outer ring. Every later ring in the same list is a hole: the file's 13 holes are places where a subzone wraps around something that belongs to a different subzone or to no subzone at all, and the hole is how the file says "not this one" without a second feature. A MultiPolygon's coordinates is one level deeper: a list of parts, each part the same outer-ring-then-holes list. The 11 MultiPolygon subzones are the ones with an islet, a reclaimed strip or a sliver that does not touch the main body; the islet is still that subzone, so it lives in that row.

Two consequences for the desk. First, "how many vertices" is a sum over every ring of every part, closing points included, and that is how the 58,530 was counted. Second, any function that decides inside from outside has to visit every ring, holes and islets alike, or it will put a point in a hole inside the subzone that surrounds the hole. Part 2's rule does that for free, which is one of the reasons it is the rule to learn first.

Part 2 · covers the even-odd rule by hand, then in code

Inside is an odd number

5 min live

The rule that decides whether a point is inside a shape is older than any software and short enough to do on paper. Draw a ray from the point in any direction to infinity and count how many edges of the shape it crosses. Odd means inside; even means outside. That is the even-odd rule, and the W3C SVG specification defines it exactly that way as one of the two fill-rule values. Rivermont (constructed) uses it on the real subzone rings because it needs no special case for holes and no knowledge of which way a ring was drawn. Mei does it by hand first, on a square with a notch cut out, because a rule you have run with a pencil is a rule you will trust when the code disagrees with the map.

LiveCount the crossings, by hand first3 min▶

Take the notched square in the figure. Point A sits in the body; its ray west meets the left edge once, one is odd, A is inside. Point B sits in the notch, which is outside the shape even though it is surrounded on three sides; its ray north crosses the notch's top edge and then the square's top edge, two is even, B is outside. Now send B's ray east instead: it crosses nothing, zero is even, same answer. Send A's ray east: it meets the notch's left wall once, same answer again. Any ray, any direction, the parity agrees, and that is why a function can pick the convenient direction (horizontal, to the right) and never think about it again.

In code the test for "does this edge cross a horizontal ray to the right of the point" is two lines: the edge's two ends straddle the point's latitude, and the longitude where the edge meets that latitude is to the right of the point. Flip a boolean each time it is true. Run the loop over every ring of every part, holes included, and read the boolean at the end. The real subzone rings are long (the biggest have thousands of corners) but the rule is the same one you just did with a pencil; the build-along runs it over 613 exits and 332 subzones, 203,516 tests, in plain Python.

Self-studyHoles for free, and the other rule3 min▶

A point inside a hole is, by the file's meaning, outside the subzone. Even-odd gets this without being told which ring is the hole: the ray from a point in the hole crosses the hole's ring once and the outer ring once, two is even, outside. A point in the solid part crosses only the outer ring, one, inside. So "sum the crossings over all rings and take the parity" is the whole algorithm, and it is why the engine behind session 6 runs even-odd over every ring and tests itself on a notched square and a square with a hole at every load.

The SVG specification names a second rule, nonzero: add one for an edge crossing the ray left to right, subtract one for right to left, and call zero outside. It gives the same answer as even-odd on well-formed rings whose holes are wound the opposite way to their outer ring, and a different answer on self-overlapping shapes, where even-odd leaves the overlap empty and nonzero fills it. GeoJSON polygons are supposed to be simple and non-overlapping, so the two agree on this file; even-odd is taught first because it asks nothing about winding direction, and the direction a ring was digitised in is exactly the kind of fact a file does not tell you.

Self-studyWhy a centroid can fall outside its own shape3 min▶

The centroid Mei will use in session 3 is the area-weighted planar centroid of all outer rings minus holes, computed in degrees, which is fine at 1 deg N and said so. It is the balance point of the shape, not a point chosen from inside it, and nothing in the arithmetic requires the balance point to lie on the shape. A C-shaped subzone balances in the gap of the C. A MultiPolygon with a mainland part and an islet balances somewhere in the water between. A long thin subzone that bends balances off its own body. When that centroid is then used as "the location of the subzone" for a join or a label, it can land in the neighbour, and the neighbour's name comes back with no error raised.

The check is one call to the function you just wrote: inside(cx, cy, geometry) on the shape's own centroid. False is not a bug in the centroid; it is a property of the shape, and the honest response is to record it, use a point known to be inside for labels, and remember in session 5 that "cluster joined to subzone by centroid" is a decision with this edge in it.

Test the function on shapes you can draw. Before the real rings, run inside on a notched square and a square with a hole and assert the four answers you can see on paper. A point-in-polygon bug on a 4,000-corner ring produces a plausible wrong zone; the same bug on a five-corner square produces an assertion error with a line number.

Part 3 · covers simplification and the boundary as a decision

The shape you draw and the layer you pick

5 min live

Rivermont is constructed; the two things that move its counts are real. The first is simplification. A boundary drawn for a web page cannot carry 58,530 corners, so the engine behind session 6 runs the Douglas-Peucker algorithm at a tolerance of 0.0003 degrees, about 33 m at this latitude, and keeps 5,326 vertices, dropping 22 degenerate rings that were tiny islets or slivers, and rounding what is left to 0.00001 degrees. Of the 613 exits, 608 then fall inside exactly one subzone, 3 fall outside every simplified boundary, and 2 fall in two, where neighbouring simplified rings overlap by a sliver. The second is the layer. The same exits counted by planning area give 55 numbers instead of 332, and an estate's "exits nearby" can change without a single exit moving.

LiveWhat simplification does to an exit near the edge3 min▶

Douglas-Peucker keeps the two ends of a ring, finds the corner farthest from the straight line between them, keeps it if it is farther than the tolerance, and recurses on each half. At 0.0003 degrees it throws away every wiggle smaller than about 33 m, and the 58,530 corners become 5,326: a 91% cut that leaves the map looking the same on a screen. The raw ring and the simplified ring disagree only in a band about 33 m wide along every edge, and the exits that live in that band are the ones that move. On this file that is five of 613: three end up outside every simplified subzone, usually an exit on a shoreline or a boundary road that the straightened line now passes on the wrong side of, and two end up inside two subzones at once, because two neighbours simplified independently can overlap by a sliver where the raw rings shared an edge exactly.

None of this is wrong. The simplified layer exists so a page can draw it; the session 6 bench says on the widget that it is working at five decimals and about 33 m. The mistake would be to publish a count from the drawing layer and call it the count. The desk's rule is that counts come from the raw rings and the drawing layer draws; when the two must differ, the page says by how much, which is what the 608, 3 and 2 are for.

Self-studyThe boundary is a decision, and it has a name4 min▶

Arif's "exits near our estate" has no answer until somebody picks the shape that "near" means. Count by subzone and there are 332 numbers; count by planning area and there are 55, each the sum of its subzones; draw a 500 m circle around the estate instead and the boundary file is not even used. The same 613 points, three honest counts, and the one Priya puts on a slide depends on which layer the analyst reached for. URA's own page says the subzones are indicative and may not match existing developments, which is a reminder that the layer was drawn for planning, not for the question being asked tonight. Write the layer next to the count, every time: "exits per subzone, URA MP2019 raw rings, counted 2026-10-22" is a number; "exits: 4" is not.

The general fact that a count or a rate changes with the zoning scheme it is aggregated into has a name, the modifiable areal unit problem, set out by Openshaw (1984, reported). How deep it goes, how it interacts with where sensors are placed, and what it does to a rate map are taught next door in Smart City; the mechanism you need tonight is the right-hand panel of the figure, and the depth is at learn-smart-city, zones, joins and the map.

Real world

The slide counted by planning area, which pulls in exits across a canal that nobody from the estate uses; Mei counted by subzone, which stops at a road the estate's residents cross every morning. ★ Step 1 · open and countimport json, sys, math f = json.load(open(sys.argv[1], encoding="utf-8")) # the URA subzone file feats = f["features"] def parts_of(geom): # a Polygon is one part; a MultiPolygon is many return [geom["coordinates"]] if geom["type"] == "Polygon" else geom["coordinates"] types, rings, holes, verts = {}, 0, 0, 0 for p in feats: g = p["geometry"]; types[g["type"]] = types.get(g["type"], 0) + 1 for part in parts_of(g): rings += len(part); holes += len(part) - 1 # ring 0 is the outer edge, the rest are holes verts += sum(len(r) for r in part) print(len(feats), types) print(rings, "rings", holes, "holes", verts, "vertices") print(len({p["properties"]["PLN_AREA_N"] for p in feats}), "planning areas", len({p["properties"]["REGION_N"] for p in feats}), "regions", sum(p["properties"]["CA_IND"] == "Y" for p in feats), "in the Central Area") print(f.get("crs")) # run: python3 -I count_subzones.py downloads/d_8594ae9ff96d0c708bc2af633048edfb.geojson # 332 {'Polygon': 321, 'MultiPolygon': 11} # 374 rings 13 holes 58530 vertices # 55 planning areas 5 regions 50 in the Central Area # None

Write the even-odd test and prove it on paper shapes. One ring at a time: an edge counts when its two ends straddle the point's latitude and the edge meets that latitude to the right of the point. Sum over every ring of every part and take the parity. The asserts are the notched square and the square with a hole from Part 2; run them before any real ring.

★ Step 2 · inside()def crosses(x, y, ring): # even-odd on one closed ring, ray to the east c = False for i in range(len(ring) - 1): (x1, y1), (x2, y2) = ring[i][:2], ring[i + 1][:2] if (y1 > y) != (y2 > y): # the edge straddles the point's latitude if x < x1 + (y - y1) * (x2 - x1) / (y2 - y1): # and meets it to the right of the point c = not c return c def inside(x, y, geom): # every ring of every part, holes included return sum(crosses(x, y, r) for part in parts_of(geom) for r in part) % 2 == 1 notch = {"type": "Polygon", "coordinates": [[(0,0),(10,0),(10,4),(6,4),(6,6),(10,6),(10,10),(0,10),(0,0)]]} holed = {"type": "Polygon", "coordinates": [[(0,0),(10,0),(10,10),(0,10),(0,0)], [(3,3),(7,3),(7,7),(3,7),(3,3)]]} assert inside(3, 5, notch) and not inside(8, 5, notch) # A in the body, B in the notch assert inside(1, 1, holed) and not inside(5, 5, holed) # the corner, and the hole print("paper shapes pass") # paper shapes pass

Way 2: simplify the rings yourself and count again. Douglas-Peucker in a dozen lines: keep the ends, keep the farthest corner if it is beyond the tolerance, recurse. A ring left with fewer than four points encloses nothing and is dropped. Compare the hit lists exit by exit; the ones that change are the exits in the 33 m band. Your vertex total will not be exactly 5,326, because the engine also rounds to 0.00001 degrees and treats degenerate rings its own way; it should be the same order of size.

★ Step 4 · way 2, simplified ringsdef dp(ring, tol): # Douglas-Peucker on one ring if len(ring) < 3: return ring (x1, y1), (x2, y2) = ring[0][:2], ring[-1][:2] dx, dy = x2 - x1, y2 - y1 best, idx = 0.0, 0 for i in range(1, len(ring) - 1): x, y = ring[i][:2] if dx == 0 and dy == 0: d = math.hypot(x - x1, y - y1) # closed ring: ends coincide else: t = max(0.0, min(1.0, ((x - x1) * dx + (y - y1) * dy) / (dx * dx + dy * dy))) d = math.hypot(x - (x1 + t * dx), y - (y1 + t * dy)) if d > best: best, idx = d, i if best <= tol: return [ring[0], ring[-1]] return dp(ring[:idx + 1], tol)[:-1] + dp(ring[idx:], tol) def simplify(geom, tol=0.0003): # about 33 m at 1 deg N out = [] for part in parts_of(geom): rs = [r for r in (dp(r, tol) for r in part) if len(r) >= 4] # a ring needs three distinct corners if rs: out.append(rs) return {"type": "MultiPolygon", "coordinates": out} simple = [simplify(p["geometry"]) for p in feats] print(sum(len(r) for g in simple for part in g["coordinates"] for r in part), "vertices after") # your number; the engine's run keeps 5,326 moved = 0 for e, hs in zip(exits, hits_raw): x, y = e["geometry"]["coordinates"][:2] hs2 = [n for n, g in zip(names, simple) if inside(x, y, g)] if hs2 != hs: moved += 1 print(e["properties"]["STATION_NA"], e["properties"]["EXIT_CODE"], hs, "->", hs2) print(moved, "exits changed zone") # your number will differ; on the engine's layer 3 land in none and 2 in two

Check yourself

Three questions

Clear all three and session 2 gets stamped in your passport.

1 · A subzone consists of a mainland part and a small islet with sea between. How does the URA file store it?

The file has 332 rows for 332 subzones and 11 of them are MultiPolygon, one row with several parts. A second ring inside a Polygon is a hole, not a separate piece, so C would cut the islet out of the subzone rather than add it; A and D invent a second row the file does not have.

2 · A point sits inside a hole of a subzone polygon. A ray from it going east crosses the hole's ring once and the outer ring once. What does the even-odd rule say?

Sum the crossings over every ring and take the parity: one plus one is two, even, outside, which is what the file means by a hole. No special case is needed, which is why the rule is run over all rings. A describes how the point looks on a map, not what the geometry says.

3 · Mei counts the 613 exits by subzone and again by planning area, and an estate's "nearby exits" number changes. No exit moved. What happened?

Both layers are in the same file and the same degrees; the rule does not care about size; and the exits did not change. What changed is the shape the question was poured into. That dependence has a name, the modifiable areal unit problem, and its depth is taught in Smart City.
