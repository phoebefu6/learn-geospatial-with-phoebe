Learn Geospatial Data with Phoebe · Session 4 of 6

Spatial joins and the grid index

A spatial join is an ordinary join with a geometric predicate where the equals sign used to be: "this exit is inside this subzone", or "this exit is within 500 m of this centroid". The predicate is the expensive part. Testing 613 exits against 332 subzones the honest way is 203,516 ray-casting tests, and tonight that is fine, because it finishes before you have put your cup down. The same loop on a million rows is not fine, and the fix is not a faster computer. It is a cheap question asked first, so the slow question is asked rarely. We ask it two ways: a bounding box per polygon, and a 500 m grid of cells kept in a dictionary. Both give exactly the answers the full loop gives. One of them does it with a single lookup per point.

Part 1 · covers the full loop and when it is fine

Every point against every polygon

5 min live

The honest way to join points to polygons is two nested loops: for each exit, for each subzone, run the even-odd test from session 2. For the real files that is 613 x 332 = 203,516 ray-casting tests, and each test walks every edge of the polygon. On a laptop it finishes in seconds. Brute force is not a mistake; it is the reference. Everything faster has to be checked against it, which means the slow loop is the first thing you write, not the thing you skip.

LiveWhat the full loop actually computes3 min▶

Two loops, one predicate. For every one of the 613 exits, for every one of the 332 subzones, cast a ray from the exit and count the polygon edges it crosses; odd is inside, even is outside, over every ring, so holes come free. That is 203,516 tests. Each test is itself a loop over the polygon's edges, and the shipped geometry for the bench carries 5,326 vertices across the 332 subzones, so the inner work is a few million edge comparisons. A laptop does that in seconds. The result on the bench geometry: 608 exits sit inside exactly one subzone, 3 inside none, because they fall outside every simplified boundary, and 2 inside two, where simplification made neighbouring boundaries overlap. Session 2 explained those five; tonight they are the fixed answer every faster method must reproduce.

Rivermont is constructed, and this is the moment at the desk where Mei runs the full loop on purpose and keeps the output file. Not because it is fast. Because it is right by construction, and "right by construction" is what you compare a clever method against. A spatial index that disagrees with brute force is a bug, every time, and you can only know that if the brute-force answer is sitting in a file.

Self-studyWhere the product stops being fine3 min▶

The cost of the full loop is the product of the two counts times the average edge count. Any one of the three can grow. The polygon count rarely does: Singapore has 332 subzones and 55 planning areas and that is that. The edge count grows when you stop simplifying: the raw URA file has 58,530 vertices against the bench's 5,326, so the same 203,516 tests do roughly eleven times the edge work on the raw boundaries (arithmetic from the two counts, not a timing). The point count is the one Arif grows. Every block, every bus stop, every tree is a new set of points against the same 332 polygons, and 1,000,000 points is 332,000,000 tests, which is arithmetic, not a measurement, and also a lunch break you did not plan for.

The professional norm is to write the full loop first, time it on the real size you expect in a year, and reach for an index only when that timing is a problem. Indexes add code, and code added without a measured reason is code that will be wrong without a measured symptom. The same logic runs on the SQL side: a join on a spatial predicate without an index is a nested loop, and a spatial database extension will tell you so in its plan. Joins in general are taught next door at learn-sql: joining tables and pandas core; only the spatial predicate lives here.

Real world

The overnight job that became a Monday job. A familiar pattern at any data desk: a point-in-polygon script written for a few hundred sites runs in a moment, so nobody times it. A year later the same script is pointed at every delivery address in the quarter. Nothing is wrong with the code. The product of two counts grew, and the first sign was the job that had not finished by the morning meeting. The fix was not a faster machine; it was asking a cheap question before the slow one, which is the rest of tonight.

Part 2 · covers the bounding-box prefilter

Ask the cheap question first

5 min live

Every polygon has a bounding box: the smallest axis-aligned rectangle that contains it, four numbers. A point outside the box cannot be inside the polygon, and that test is four comparisons instead of a walk along every edge. On the real files the box says yes 1,283 times out of 203,516, and 671 of those yeses are wrong: the point is in the box but not in the shape. The exact test is run only on the 1,283 candidates, and it rejects the 671. The answers are identical to brute force. The box never says no wrongly; it only says yes too often, and that is exactly the kind of error a second test can fix.

LiveCandidate, then exact3 min▶

The prefilter has one job: produce a candidate list that is guaranteed to contain every true match and is allowed to contain extras. Guaranteed is the important word. A box that is too small would say no to a true match and that error could never be repaired downstream; a box that is exactly the polygon's extent can only err by saying yes. Then the exact test, the even-odd ray from session 2, runs on the candidates alone and removes the extras. On the real files that is 1,283 exact tests against 203,516, and the 671 false box hits are the price of a filter that is four comparisons long. 1,283 minus 671 is 612 true pairs, which is the 608 exits inside one subzone plus the 2 exits counted in two.

Rivermont is constructed; the arithmetic is from the real files. Mei's check is the one that matters: the join table from the box-then-exact run is byte-for-byte the join table from the full loop. If it were not, the box would be too small somewhere, and that is a bug to find now rather than a wrong count to explain to Priya later.

Self-studyWhy the box test is still 203,516 tests3 min▶

Look at the counts again. The bounding box cut the exact tests from 203,516 to 1,283, but the box test itself still ran 203,516 times: for every exit, it compared against all 332 boxes. The win is that each of those tests is four comparisons instead of a walk along a polygon's edges, so the total work is far smaller. The number of questions asked did not drop. The cost of each question did. That is the first of two kinds of speed-up, and it is the one with a ceiling: at a million points you still ask 332 million box questions, cheap as each one is.

The second kind of speed-up drops the number of questions, and it needs a structure that can answer "which polygons could possibly contain this point?" without looking at all 332 of them. That is what an index is, and Part 3 builds the simplest one that works. Long, thin and diagonal polygons are the bounding box's worst case: a river-shaped subzone fills a small fraction of its own box, so most box hits on it are false. The 671 false hits across the real files are mostly that shape of problem, which is why the exact test is never optional.

The prefilter may only err in one direction. Whatever cheap test you put in front of an expensive one, it must never reject a true match. Yes-too-often is repairable by the exact test; no-when-it-should-be-yes is a silent wrong answer. Write that sentence next to the prefilter and test it by comparing against brute force on the real data.

Part 3 · covers a grid-cell index from scratch

A dictionary of cells

5 min live

Lay a grid of 500 m cells over Singapore in SVY21 metres. The cell a point falls in is two integer divisions: floor(E / 500), floor(N / 500). Put that pair in a dictionary as the key, and as the value the list of polygons whose bounding box covers that cell. Now a point asks one question: "what is in my cell?" The answer comes from a hash lookup, not from 332 box tests, and the exact test runs on that short list. On the real files that is 2,396 exact tests after one lookup per exit, same answers as brute force. The nearest-exit query uses the same grid the other way round, looking in the point's own cell first and widening ring by ring: 5,528 distance evaluations for the nearest exit and the 500 m catchment together, against 203,516 for the full loop, and the same 332 nearest exits.

LiveBuilding the grid, and the trade it makes3 min▶

Building the index is one pass over the polygons. For each subzone, take its bounding box, work out which cells the box touches (from floor(min E / 500) to floor(max E / 500), the same for N) and append the subzone's id to each of those cells' lists. A subzone a few kilometres across lands in a few dozen cells; a sliver lands in one or two. Querying is one pass over the points: look up the point's cell, run the exact test on every subzone in that list. No box tests at all, because the cell was built from the boxes.

Read the two counts side by side, because they teach the trade. The bounding-box run made 1,283 exact tests; the grid run makes 2,396. The grid does more exact work, about 1,100 extra tests (arithmetic from the two counts), because a 500 m cell is coarser than a polygon's own box: a cell at the corner of a subzone's box is in that subzone's list even where the box barely clips it. What the grid removed was the 203,516 box tests, replacing them with 613 dictionary lookups. That is the second kind of speed-up, the one that drops the number of questions, and it is the one that survives a million points. Rivermont is constructed, and Mei picks 500 m because it is the catchment radius Arif asked about in session 3, so the same grid answers both the join and the nearest query.

Self-studyNearest by expanding rings, and when to stop4 min▶

Index the 613 exits by cell the same way. To find the nearest exit to a subzone centroid, look in the centroid's own cell (ring 0) and measure every exit there. Then the eight cells around it (ring 1), then the sixteen around those (ring 2). After finishing ring r, any exit in ring r + 1 or beyond is at least r cells away in a straight line, so if the best distance found so far is at most r x 500 m, no farther ring can hold anything nearer, and you stop. That stopping rule is the whole algorithm, and it is why the query is exact and not approximate: it never guesses, it only declines to look where nothing nearer can be. On the bench geometry the nearest exit and the 500 m catchment for all 332 centroids cost 5,528 distance evaluations against 203,516 for the full loop, and the 332 nearest exits are the same ones, with the same median of 610.38 m.

The cell size is a dial. Cells too small and the rings expand many times through empty cells before they find anything; cells too big and each cell holds so many points that the lookup saves little. 500 m is a sensible size when the typical nearest distance is a few hundred metres, which is what session 3 measured. Real spatial indexes, the R-tree in a spatial database extension or a desktop GIS, are trees of nested bounding boxes rather than a flat grid, and they adapt the cell to the data instead of asking you to pick 500. The pattern is unchanged: a cheap structure returns candidates, the exact predicate decides. When a query plan says "index scan" on a spatial join, this is what it means.

★ Step 1 · brute force, the referenceimport json, sys, math from collections import Counter # paste svy21(lon, lat) from session 1, step 3, here def rings_of(g): # Polygon -> its rings; MultiPolygon -> every ring of every part return g["coordinates"] if g["type"] == "Polygon" else [r for part in g["coordinates"] for r in part] def inside(x, y, rings): # even-odd over every ring: holes come free (session 2) c = False for ring in rings: for k in range(len(ring)): (x1, y1), (x2, y2) = ring[k - 1], ring[k] if (y1 > y) != (y2 > y) and x < x1 + (y - y1) * (x2 - x1) / (y2 - y1): c = not c return c sub = json.load(open(sys.argv[1], encoding="utf-8"))["features"] # 332 subzones ex = json.load(open(sys.argv[2], encoding="utf-8"))["features"] # 613 exits polys = [(f["properties"]["SUBZONE_N"], [[svy21(x, y) for x, y, *_ in r] for r in rings_of(f["geometry"])]) for f in sub] pts = [(p["properties"]["STATION_NA"] + " " + p["properties"]["EXIT_CODE"], svy21(*p["geometry"]["coordinates"][:2])) for p in ex] tests, brute = 0, {} for i, (name, (E, N)) in enumerate(pts): hits = [] for j, (zone, rings) in enumerate(polys): tests += 1 if inside(E, N, rings): hits.append(j) brute[i] = hits print(len(polys), len(pts), tests) # 332 613 203516 (the product is the same on any version of the files) print(Counter(len(h) for h in brute.values())) # bench geometry: Counter({1: 608, 0: 3, 2: 2}); raw file: your numbers will differ

Put a bounding box in front of the exact test, and assert nothing changed. Four comparisons per pair, then the slow test on the candidates only. The assert is the point of the step: a prefilter that changes the answer is a bug, not an optimisation.

★ Step 2 · box, then exactdef bbox(rings): xs = [x for r in rings for x, y in r]; ys = [y for r in rings for x, y in r] return min(xs), min(ys), max(xs), max(ys) boxes = [bbox(rings) for zone, rings in polys] box_hits, exact, viabox = 0, 0, {} for i, (name, (E, N)) in enumerate(pts): hits = [] for j, (x0, y0, x1, y1) in enumerate(boxes): if x0 <= E <= x1 and y0 <= N <= y1: # the cheap question: four comparisons box_hits += 1; exact += 1 if inside(E, N, polys[j][1]): hits.append(j) viabox[i] = hits assert viabox == brute # same answers, or the box is too small somewhere true_pairs = sum(len(h) for h in brute.values()) print(box_hits, box_hits - true_pairs, exact) # bench geometry: 1283 671 1283; raw file: your numbers will differ

Build the grid. One dictionary, keyed by cell. For each subzone, every cell its bounding box touches gets the subzone's index appended. This is the whole index, and it is built once.

★ Step 3 · the index is a dictionaryCELL = 500.0 # metres, in SVY21; also the catchment radius from session 3 def key(E, N): return (math.floor(E / CELL), math.floor(N / CELL)) grid = {} # cell key -> subzone indexes whose box covers the cell for j, (x0, y0, x1, y1) in enumerate(boxes): (cx0, cy0), (cx1, cy1) = key(x0, y0), key(x1, y1) for cx in range(cx0, cx1 + 1): for cy in range(cy0, cy1 + 1): grid.setdefault((cx, cy), []).append(j) print(len(grid), max(len(v) for v in grid.values())) # cells used, busiest cell: your numbers will differ (not in the map)

Query the grid and assert against brute force again. One lookup per exit instead of 332 box tests, then the exact test on the cell's list. Expect more exact tests than step 2 and no box tests at all; that is the trade Part 3 described.

★ Step 4 · one lookup, then exactexact, viagrid = 0, {} for i, (name, (E, N)) in enumerate(pts): hits = [] for j in grid.get(key(E, N), []): # ONE dictionary lookup replaces 332 box tests exact += 1 if inside(E, N, polys[j][1]): hits.append(j) viagrid[i] = hits assert viagrid == brute # the index may shorten the list; it may not change the answer print(exact) # bench geometry: 2396; raw file: your number will differ for i in list(brute)[:3]: # the join table, first three rows; your rows follow your file's order print(pts[i][0], "->", [polys[j][0] for j in brute[i]])

Nearest exit by expanding rings, checked against the full loop. Index the exits by cell, then for each subzone centroid look in ring 0, ring 1, ring 2 and stop once the best so far is nearer than the next ring could be. The centroid is the area-weighted one from session 2, here in metres. Compare distances, not indexes, so two exits at the same distance cannot fail the check for the wrong reason.

★ Step 5 · expanding ringsegrid = {} # cell key -> exit indexes for i, (name, (E, N)) in enumerate(pts): egrid.setdefault(key(E, N), []).append(i) def nearest(E, N): cx, cy = key(E, N); best, evals, r = (math.inf, None), 0, 0 while True: for dx in range(-r, r + 1): for dy in range(-r, r + 1): if max(abs(dx), abs(dy)) != r: continue # only the cells new to this ring for i in egrid.get((cx + dx, cy + dy), []): d = math.dist((E, N), pts[i][1]); evals += 1 if d < best[0]: best = (d, i) if best[1] is not None and best[0] <= r * CELL: # nothing in a farther ring can be nearer return best, evals r += 1 def centroid(rings): # area-weighted planar centroid, all rings (session 2) A = Cx = Cy = 0.0 for ring in rings: for k in range(len(ring)): (x1, y1), (x2, y2) = ring[k - 1], ring[k] w = x1 * y2 - x2 * y1 A += w; Cx += (x1 + x2) * w; Cy += (y1 + y2) * w return Cx / (3 * A), Cy / (3 * A) cents = [centroid(rings) for zone, rings in polys] brute_d = [min(math.dist(c, q) for name, q in pts) for c in cents] # 332 x 613 = 203,516 evaluations grid_d, grid_evals = [], 0 for c in cents: (d, i), ev = nearest(*c); grid_d.append(d); grid_evals += ev assert all(abs(a - b) < 1e-6 for a, b in zip(brute_d, grid_d)) # same 332 nearest distances print(len(cents) * len(pts), grid_evals) # 203516 and your own count; the bench's 5528 includes the 500 m catchment too print(sorted(grid_d)[len(grid_d) // 2]) # bench geometry median 610.38 m; raw file and metre centroids: your number will differ

Keep the brute-force output as a fixture. The three asserts above are the deliverable, not the speed. Save the full-loop join table once; every later index, yours or a spatial database extension's, gets compared against that file before anyone trusts its count. An index that is fast and slightly wrong is the most expensive kind of code a desk can own.

Check yourself

Three questions

Clear all three and session 4 gets stamped in your passport.

1 · The bounding-box prefilter said yes 1,283 times on the real files and 671 of those were false. Why is that acceptable?

The candidate list may contain extras because the exact test removes them; it may not miss a true match because nothing downstream can add it back. A treats the 671 as an error in the answer, which they are not: the answers are identical to brute force. C would make the join wrong. D shrinks the box past the polygon and creates exactly the unrepairable error.

2 · The grid index ran 2,396 exact tests, more than the bounding box's 1,283. In what sense is it the faster method?

The box made each question cheaper but still asked all 203,516 of them; the grid drops the question count to one lookup per point, at the price of about 1,100 extra exact tests because a 500 m cell is coarser than a polygon's own box. B is false: the exact test is the same function in both runs. D would change the answer, and the three asserts forbid that.

3 · In the expanding-ring nearest query, when is it safe to stop after finishing ring r?

The stopping rule compares the best distance so far with the gap to the next ring; that is what makes the query exact rather than approximate. B fails when the query point sits near a cell edge and a nearer exit lies just across it. C assumes a density the data does not promise. D stops too early in a sparse area where the next ring out is the one with the exit.
