Where is this row?

A row with 103.80618 in one column and 1.29425 in the other looks like a place. It is a claim. Behind it sit three things that can each be wrong without an error message: the reference system that says what the numbers mean, the boundary that will later turn the point into a zone, and the formula that will turn two points into a distance. Tonight is the first of the three. We read a real file of 613 MRT station exits, name the system its numbers live in, write the same row in Singapore's own metre grid, and run the one check that catches the commonest mistake in any table with a latitude column: the two numbers in the wrong order.

Part 1 · covers a coordinate is a claim with a reference system

Two numbers are not a place

5 min live

A coordinate reference system (CRS) is the rule that turns numbers into a position: which shape of the Earth, which origin, which units, which axis comes first. The exits file carries pairs like [103.80618, 1.29425]. Those are degrees on the WGS 84 ellipsoid, longitude first, because that is what GeoJSON means when it says nothing. Singapore's land survey uses a different rule: SVY21, EPSG:3414, metres east and north of an origin near the middle of the island. The same exit is (24,979.7, 30,737.1) there. Neither pair is "the location". Each is the location under a named rule, and the rule travels with the number or the number is noise.

LiveWGS 84 and the code that names it3 min▶

Latitude and longitude are angles, and an angle needs a shape to be measured on. WGS 84 is the ellipsoid behind satellite positioning: semi-major axis 6,378,137 m, flattening 1/298.257223563. The EPSG registry gives every reference system a number so that software can name it without ambiguity; WGS 84 degrees are EPSG:4326. GeoJSON, the format the exits file uses, does not carry a system name at all. It fixes one by convention: WGS 84, and coordinates written longitude first. The file Mei opened has no crs member, so the convention is the rule, and the first thing she writes in the desk's notes is "exits: EPSG:4326, [long, lat]".

That line is the habit of the session. A coordinate that arrives without its system is not wrong, it is unverified, and the fix is cheap when the file is open and expensive after the numbers have been joined, summed and put on a map.

Self-studySVY21: Singapore's metre grid, and the control point that proves a conversion4 min▶

SVY21 / Singapore TM is EPSG:3414, read in the EPSG registry: a transverse Mercator projection with its natural origin at 1 deg 22' N, 103 deg 50' E, scale factor 1, false easting 28,001.642 m and false northing 38,744.572 m, on the WGS 84 ellipsoid (the SVY21 datum, EPSG:4757). Its area of use is Singapore onshore and offshore, 1.13 to 1.47 N and 103.59 to 104.07 E, and the registry remarks that for cadastral purposes it replaced the Kertau 1968 Singapore Grid (EPSG:24500) from August 2004. The axis order in the registry is northing then easting, which is a second place the two numbers can be swapped.

A projection's definition gives you a free test. The natural origin maps to exactly the false easting and false northing: feed (103 deg 50' E, 1 deg 22' N) into your function and it must return (28,001.642, 38,744.572) to the millimetre. The engine behind session 6 runs that test on every page load and fails loudly if a parameter is off by one metre. A second, independent series implementation agreed with it on all 945 shipped points to under a micrometre. That is what "verified" means for a conversion: not that the numbers look plausible, but that a point whose answer is known by definition comes out right.

Real world

Two exports, both labelled X and Y. A familiar pattern at any data desk: one team exports from a survey system in SVY21 metres, another from a web form in degrees, and both spreadsheets have columns called X and Y. Joined on an address, the table looks fine. Mapped, half the points sit in the Indian Ocean. The error is not in either export. It is in the join, where a system name was never asked for because the column headers looked the same.

Part 2 · covers what a degree is worth at 1 deg N

A degree is an angle, not a length

5 min live

The tempting shortcut is to treat degrees as a flat grid and multiply by one constant. The constant most people reach for is 111,320 m: the length of one degree of longitude at the equator, 2 pi times 6,378,137 m divided by 360. It is almost right in Singapore for two reasons that both stop being true as you move north, and the mechanism is one cosine.

LiveWhy the shortcut almost works here3 min▶

A degree of longitude is 111.32 km at the equator and shrinks by cos(latitude) as you go north: at 1 deg 22' N the cosine is 0.99972, so a degree is 111.29 km, 30 m short of the constant. A degree of latitude is a different length again, about 110.57 km near the equator, because the Earth is flattened and a meridian arc near the equator is shorter than a parallel. So the constant 111,320 is 0.03% long on east-west distances in Singapore and 0.7% long on north-south ones. Across the island's roughly 50 km those errors are tens of metres, which is why the shortcut survives in so many spreadsheets.

Session 3 measures it on the real exits: nearest exit per subzone centroid by raw degrees is 3.79 m too long on average and 57 m too long at worst against SVY21 metres. Then it moves the same points to 60 deg N, where the cosine is 0.5 and the average error becomes 276 m. Nothing about the formula changed. The latitude did.

Self-studyThe sphere is the bigger error near the equator3 min▶

The next step up from a constant is the haversine formula: great-circle distance on a sphere, radius 6,371,008.8 m, with the latitude inside the formula so the cosine is handled for free. It is the standard answer and it is usually good enough. In Singapore it is only slightly better than the constant: 2.57 m too long on average and 43 m at worst against projected metres, because a sphere of one radius cannot be right about both a 110.57 km meridian degree and a 111.32 km equatorial degree at once. Near the equator the ellipsoid is the bigger source of error and the cosine the smaller one; at 60 deg N the order flips. The formula that gets both right is the projection itself, which is why SVY21 metres are the reference in session 6 and why the ellipsoidal great-circle method (Vincenty 1975, reported) exists for the cases a local projection cannot cover.

Say the latitude when you say the error. "Raw degrees are fine" is true at 1 deg N and false at 60 deg N. A method that works for Singapore and is copied to a dataset about Helsinki fails by a factor of two without a single line changing. Write the latitude range next to the method in the notes.

Part 3 · covers axis order traps

Which number comes first

5 min live

People say "latitude, longitude". GeoJSON writes [longitude, latitude]. The EPSG registry lists SVY21's axes as northing then easting. Three conventions, two orders, and a swap produces numbers that still look like numbers. The test is a range check, and it belongs at the top of every pipeline, before any distance is computed.

LiveThree conventions and the one test3 min▶

Spoken English, most spreadsheets and many map interfaces put latitude first. GeoJSON and most programming libraries put longitude first, because longitude is the x axis and latitude the y axis of a flat drawing. The EPSG registry records SVY21 with northing before easting. None of these is wrong; the trap is moving between them without saying so. A swapped exit in Singapore lands near 1.29 E, 103.81 N, a latitude that cannot exist. A swapped point near the equator in the Atlantic, where longitude is also small, would pass unnoticed, which is why the check has two parts: the universal one (|latitude| <= 90, |longitude| <= 180) and the local one (the bounding box of the place the data is about).

Session 6 has a button that swaps the two columns on all 613 exits and recomputes everything. The result is not subtle: 332 of 332 subzones contain zero exits, and the median nearest exit is 9,531 km away. The largest "latitude" is 103.989. One line of range checking would have stopped it at row 1.

Self-studyPrecision is not accuracy2 min▶

The exits file carries coordinates to 14 decimal places. At 1 deg N, the fifth decimal of a degree is about 1.1 m and the seventh about 1 cm; everything after that is arithmetic residue, not survey precision. The shipped data for session 6 keeps five decimals, which is why the bench says so on the widget, and the subzone boundaries are simplified to about 33 m tolerance for the page, which is why three exits fall outside every simplified boundary. Fourteen decimals on a point that was digitised from a plan is a precision claim nobody made. Record the precision you believe, not the one the file prints.

Real world

Arif's spreadsheet (constructed). Arif arrives with a list of estate blocks he typed from a planning portal, columns "Lat" and "Long". Two rows have the numbers the other way round, because he read them off a page that showed them longitude first. Mei does not look for them by eye. She runs the range check on the whole sheet and it names the two rows. The desk's rule is that a coordinate column is validated the way a date column is: by shape, before by content.

Write the conversion, then prove it on the origin. The EPSG:3414 parameters go in by name. The series below is the standard transverse Mercator forward formula for an ellipsoid; the test at the end is the one that matters: the natural origin must return the false easting and northing exactly.

★ Step 3 · svy21()import math A, F = 6378137.0, 1 / 298.257223563 # WGS 84 ellipsoid (EPSG:4757 SVY21 datum) LAT0, LON0 = 1 + 22 / 60, 103 + 50 / 60 # natural origin, degrees FE, FN, K0 = 28001.642, 38744.572, 1.0 # false easting, false northing, scale factor E2 = 2 * F - F * F; EP2 = E2 / (1 - E2); E4 = E2 * E2; E6 = E4 * E2 def merid(phi): # meridian arc from the equator, metres return A * ((1 - E2/4 - 3*E4/64 - 5*E6/256) * phi - (3*E2/8 + 3*E4/32 + 45*E6/1024) * math.sin(2*phi) + (15*E4/256 + 45*E6/1024) * math.sin(4*phi) - (35*E6/3072) * math.sin(6*phi)) M0 = merid(math.radians(LAT0)) def svy21(lon, lat): phi, lam = math.radians(lat), math.radians(lon) s, c, t = math.sin(phi), math.cos(phi), math.tan(phi) n = A / math.sqrt(1 - E2 * s * s); tt = t * t; cc = EP2 * c * c a1 = (lam - math.radians(LON0)) * c; a2 = a1*a1; a3 = a2*a1; a4 = a3*a1; a5 = a4*a1; a6 = a5*a1 x = K0 * n * (a1 + (1 - tt + cc) * a3/6 + (5 - 18*tt + tt*tt + 72*cc - 58*EP2) * a5/120) y = K0 * (merid(phi) - M0 + n * t * (a2/2 + (5 - tt + 9*cc + 4*cc*cc) * a4/24 + (61 - 58*tt + tt*tt + 600*cc - 330*EP2) * a6/720)) return FE + x, FN + y assert svy21(LON0, LAT0) == (28001.642, 38744.572) # the control point, by definition

Check yourself

Three questions

Clear all three and session 1 gets stamped in your passport.

1 · A GeoJSON file has no crs member and its first coordinate is [103.80618, 1.29425]. What does the row mean?

GeoJSON's default is WGS 84 with longitude first, so an absent crs is itself the answer. B reads the pair in the spoken order and produces an impossible latitude; D would need values in the tens of thousands. A is overcautious: the convention is the publisher's statement.

2 · Multiplying degree differences by 111,320 m per degree on both axes is almost right in Singapore. Why does the same code fail at 60 deg N?

The mechanism is one cosine on the longitude axis. B points at the ellipsoid, which is the smaller effect and already present at the equator; D is true but irrelevant, since the raw-degree shortcut uses no projection at all.

3 · Arif's sheet has columns Lat and Long, and two rows have the values swapped. What catches them before any distance is computed?

The conversion formula happily computes nonsense for a latitude of 103.8 and raises nothing; a plot finds the problem only after the pipeline has run; sorting finds extremes but not a swap that lands inside the range. The range check names the rows at the top of the pipeline.
